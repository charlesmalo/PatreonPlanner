# 01. Project Rules

## Project Type

PatreonPlanner: a web application where a creator's Patreon patrons suggest films
and shows, upvote each other's picks, and see what is coming up — with who may
suggest and vote decided by the creator's own Patreon tiers.

A standalone repository, unrelated to any sibling project in the workspace.

## Tech Stack

Chosen and in production use. This table records what is; changing any row is an
architectural decision (`02_COLLABORATION_PROTOCOL.md` §1).

| Language                | TypeScript 5.5                                    | yes    |

| Frontend                | React 18 + Vite + Tailwind                        | yes    |

## The Verification Commands

There is no single command. Work is verified by all four, and a claim of "done"
quotes the ones that were run:

```
pnpm -r typecheck                          # types across every package
pnpm -r test                               # API and web unit/integration suites
pnpm format:check                          # formatting
cd e2e && pnpm e2e                         # end-to-end, needs the Docker stack up
```

A fifth is available but not part of the gate, because it re-runs the whole API
suite and is slow to sit in the loop:

```
cd apps/api && pnpm coverage               # thresholds in jest-e2e.json
```

`pnpm -r test` transpiles without typechecking, so **a green test run does not
imply a green build.** Both are required; that gap has broken a Docker build in
this project before.

If any of these fails, the work is not done. See `07_TESTING_STANDARDS.md`.

## Unbreakable Constraints

1. **The verification commands are the gate.** Types, tests, and formatting all
   run before "done".
2. **Free tooling only.** Every dependency and hosted service must be free
   unless the engineer reopens the decision. No paid APIs — this rules out
   hosted embedding, moderation, and search services, and it is why embeddings
   run locally on CPU.
3. **No new dependency without approval.** Every dependency is a decision.
4. **No unnecessary changes.** Touch only what the approved task requires.
   Opportunistic refactoring or reformatting needs approval first.
5. **No suppression to make a gate pass.** Never add a lint suppression, disable
   a rule, or lower a threshold to reach green.
6. **Migrations are hand-written** under `apps/api/prisma/migrations/`, never
   generated by `prisma migrate dev`. Partial and expression indexes this
   project depends on cannot survive a regenerate.
   - **A migration that back-fills or de-duplicates must be run against data
     shaped like production's, not only against the empty database the test
     containers give it.** Integration tests migrate a fresh schema, where a
     de-duplication step has nothing to de-duplicate and passes vacuously.
   - **Destructive changes are expand/contract.** A rolling deploy runs old and
     new code against one database for the length of the rollout, so a dropped
     column is still in the old instance's `SELECT` list and a column made
     `NOT NULL` has no default in its `INSERT`. Add and backfill in one
     release, stop reading the old shape in the next, drop it in a third.
     `apps/api/test/migration-safety.e2e-spec.ts` enforces this; migrations
     written before it exists are listed there with the reason each is exempt.
     **Never edit an applied migration to fix one** — Prisma checksums it, and
     the edit fails every database that already ran it.
   - **De-duplication needs a total order.** `DELETE ... WHERE a.createdAt >
b.createdAt` keeps _both_ rows when two share a timestamp — and rows written
     by one statement always do. The unique index that follows then fails, and it
     fails on deploy rather than in CI. Order on `(createdAt, id)`.
7. **Multi-tenancy is absolute.** Every creator-scoped query filters on
   `creatorId`. No creator or moderator may affect another creator's board. This
   is the most heavily tested property in the system and the one review has
   caught real bugs in most often.

## Privacy Constraints

- Never commit credentials, tokens, API keys, or personal data.
- Never write machine-specific absolute paths into committed files. Use
  repository-relative paths everywhere, including docs and audit logs.
- Never commit user names, host names, or local directory layouts.

See `06_SECURITY_STANDARDS.md`.
